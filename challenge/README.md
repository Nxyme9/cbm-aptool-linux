# CBM forensic challenge (Wave 5K)

Recover the flag hidden in a synthetic 64 MiB disk image. Nothing here touches
a real device or a vendor binary: the image is generated by a script and the
container is encrypted by this repository's own clean-room TEA core.

## Generate

Build the tool first (`make`), then:

```sh
python3 challenge/generate.py --out disk.img
```

`--out` is the **image file path** (the generator refuses to overwrite it).
The image is sparse: a nominal DJ MBR at LBA 0 and one TEA-encrypted CBM
container at LBA 4096, whose plaintext body holds the flag. No image blob is
committed.

## Solve

```sh
sh solver/solve.sh disk.img
```

The solver prints only the recovered flag, e.g.
`CBMCTF{tea_cbc_clean_room_2026}`. Its exit status is 0 on success, 2 on usage
error, 1 when no flag is found. It is read-only on the image; all scratch files
(carved containers, JSON report, decrypted bodies) go to a temporary directory
under `/tmp/opencode`.

## Hints

1. `cbm-tool scan <image> --carve <dir> --json <report>` finds structural
   container candidates and writes `hit-NNN-<offset>.cbm` files. Scan is
   read-only; only `--carve` and `--json` write, to the paths you name.
2. The container envelope and the 85687-byte encrypted body are described in
   [`docs/container-format.md`](../docs/container-format.md); byte 0 is
   preserved in the clear.
3. The body uses the clean-room TEA-CBC core. The crypto is native by default;
   `cbm-tool container <file> --dump-plain <out>` decrypts with the allowlisted
   published test key. No vendor PE is needed (`CBM_PE_PATH` is opt-in).
4. The plaintext is deterministic and printable, with the flag on a fixed
   offset. `cbm-tool container --strings` or a plain `grep -a` both work.

The full reverse-engineering journey, including the honest gaps, is in
[`WRITEUP.md`](../WRITEUP.md).
